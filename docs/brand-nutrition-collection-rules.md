# 브랜드 메뉴·영양정보 수집 규칙

최종 갱신: 2026-10-22

이 저장소에서 브랜드 메뉴·영양정보를 수집하거나 기존 결과를 수정·재출력할 때마다 **작업 시작 전에 이 문서 전체를 읽는다**. 터미널이나 대화가 달라도 동일하게 적용한다. 사용자의 새 지시가 이 문서보다 우선하며, 변경 사항은 이 문서와 관련 Notion 설명에도 반영한다. 결과 파일을 만들기 전에 원본과 현재 Notion 첨부 파일을 확인한다.

## 1. 수집 범위와 출처

- 브랜드 공식 홈페이지·공식 제공 자료만 사용한다.
- 요청 범위의 모든 하위 카테고리·개별 상세 페이지·공식 사이즈·온도·도우·옵션을 확인한다. 같은 제품이 여러 목록에 노출되면 한 번만 수집한다.
- 메뉴 카테고리는 실제 메뉴에 맞게 분리한다. 이름 일부가 같거나 카테고리가 같다고 다른 제품을 합치지 않는다.
- 공식 자료 간 값이 충돌할 때 사용자가 우선 출처를 지정하면 해당 메뉴·옵션은 지정한 출처의 값만 남기고, 다른 출처의 충돌 행은 삭제한다. 우선 출처와 적용 범위를 브랜드별로 기록하며 다른 미해결 사유가 없으면 정상 처리한다.
- 공식 출처 링크, 실제 수집일, 확인 가능한 영양성분 공시일·게시일·개정일을 브랜드별 Notion 페이지에 기록한다. 공시일을 못 찾으면 `공식 자료 및 홈페이지에서 확인되지 않음`으로 표시한다. 이미지 파일 경로 날짜를 공시일로 추정하지 않는다.

## 2. 표준 열과 파일

정상 파일은 다음 22열의 이름과 순서를 그대로 사용한다.

```text
메뉴,브랜드,브랜드 카테고리,메뉴 카테고리,중량 단위,중량,단위량,칼로리,탄수화물,당류,당알코올,식이섬유,단백질,지방,포화지방,트랜스지방,불포화지방,나트륨,카페인,칼륨,콜레스테롤,알코올
```

- 브랜드별로 정상 메뉴와 처리 필요 메뉴 Excel 두 개를 만든다. 처리 필요가 없어도 헤더만 있는 파일을 제공한다.
- 정상 파일은 `import_template` 데이터 시트 하나만 둔다.
- 처리 필요 파일은 동일한 22열 뒤에 `처리 유형`, `처리 사유`만 추가하고 `needs_review` 시트 하나만 둔다.
- `summary`, 원본 구분·원본 데이터·중복 횟수 등의 보조 열이나 시트는 만들지 않는다.

## 3. 중량 단위의 숫자 코드

`중량 단위` 셀에는 문자열 대신 **숫자**를 저장한다.

| 공식 단위 | 저장값 |
| --- | --- |
| g | 0 |
| ml | 1 |
| 단위 미공개·확정 불가·지원하지 않는 단위 | 공란 |

- 숫자 `0`은 유효한 g 코드이므로 falsy 검사로 공란 처리하지 않는다.
- 원본의 g/ml 기준은 보존하고 표현만 코드로 바꾼다. g↔ml 변환은 하지 않는다.
- **음료 컵 용량 oz는 브랜드 공통 사용자 지정 대응값으로 환산한다: 12oz=355ml, 16oz=473ml, 22oz=650ml.** 해당 숫자를 중량에 저장하고 중량 단위는 숫자 `1(ml)`로 기록한다. 이 단위 문제만이 처리 사유였다면 정상으로 옮기며 영양성분은 재계산하지 않는다.
- 공식 g/ml 제공량이 별도로 있으면 그 값을 우선 유지한다. 위 대응값은 음료 컵 용량 oz에 적용하며 중량 oz에 적용하지 않는다. 14oz·32oz 등 지정되지 않은 크기는 임의 환산하지 않고 중량 단위 공란과 원래 oz·숫자를 처리 사유에 보존한다.
- `12oz/16oz`처럼 여러 크기가 함께 적혀 메뉴별 대응이 불명확하면 환산표만으로 하나를 선택하지 않는다. 메뉴별 공식 근거나 별도 사용자 지정이 있어야 적용한다. 브랜드별로 확정된 선택 예외는 9절을 따른다.
- 중량 값과 영양성분은 같은 제공 기준을 사용한다. 1회 제공량·100g당·150g당·총중량을 혼용하지 않는다.
- 음료는 공식 용량, 사이드는 공식 1회분 중량을 우선한다. 공식 근거 없이 중량을 추정하지 않는다.
- 사용자가 확정한 중량·용량은 공식 미공개 제공량을 보완하는 기준으로 사용한다. 브랜드·메뉴·사이즈·온도 등 적용 옵션과 지정값을 9절 및 관련 Notion 설명에 기록하고, 별도 지시가 없으면 영양값은 재계산하지 않는다. 지정 범위 밖의 메뉴에 자동 적용하지 않는다.

## 4. 영양값과 ‘미만·이하’ 부호 규칙

- 공식 제공값만 기록한다. 미공개·하이픈은 공란으로 두며, 임의 추정하거나 0으로 대체하지 않는다. 공식 숫자 0은 그대로 유지한다.
- **음수는 해당 절댓값 미만·이하라는 부호 표현이다.** 사용자 지시에 따라 ‘이하’도 ‘미만’과 동일하게 인코딩한다. 실제 음의 함량이나 측정값이 아니며, 이 저장 방식에서는 미만과 이하를 구분하지 않는다.

| 원문 예 | 숫자 셀 저장값 | 의미 |
| --- | --- | --- |
| 5g 미만 / 5 미만 | -5 | 5 미만 |
| 0.5g 미만 / 0.5미만 | -0.5 | 0.5 미만 |
| 1mg 미만 / <1mg | -1 | 1 미만 |
| 5g 이하 / 5이하 / ≤5g / <=5g | -5 | 5 이하를 미만과 동일하게 취급 |
| 10mg이하 / 10 이하 | -10 | 10 이하를 미만과 동일하게 취급 |
| 0 | 0 | 공식값 0 |

- 단위를 제거한 숫자의 음수를 해당 중량·영양성분 열에 기록한다. 문자열 `-5`가 아니라 숫자 `-5`로 저장한다. 소수점은 보존한다.
- 다른 검토 사유가 없는 ‘미만·이하’ 행은 이 인코딩만으로 정상 파일에 포함할 수 있다. 기존 처리 사유가 ‘미만’ 또는 ‘이하’뿐이었다면 정상으로 옮긴다. 다른 문제는 유지한다.
- ‘이하’ 및 같은 의미의 `≤`, `<=`도 ‘미만’과 동일하게 해당 숫자의 음수로 저장한다. ‘이상·초과’ 등 다른 부호 표현은 사용자 지시 없이 음수 규칙으로 변환하지 않는다.
- `0 미만`, `0 이하`는 음수 0으로 의미를 보존할 수 없으므로 원문을 보존해 검토한다.
- 단위가 의심되면 임의 환산하지 않는다. 예를 들어 콜레스테롤의 공식 g 표기가 오기인지 확인되지 않으면 원문 단위를 보존하고 검토한다.
- 사용자가 단위 오기로 확정한 값은 숫자 크기를 유지하고 지정한 단위로 수정한다. 예: `215kcl`을 215kcal로 해석해 숫자 `215`로 저장한다. 적용한 브랜드·메뉴·항목과 원문·수정 단위를 기록하며, 확인되지 않은 다른 오기에 자동 적용하지 않는다.
- 복합값·범위값은 위 규칙으로 인코딩하는 ‘미만·이하’ 표현과 구별한다. 해당 열에 원문을 보존하고 검토한다.

## 5. 단위량

- **잔 단위로 제공되어 마시는 커피·음료는 단위량을 `1잔`으로 통일한다.** 원본이나 기존 파일에 `1회분`, `1회 제공량`이 있어도 이 규칙을 우선한다. HOT·ICE 및 사이즈별 메뉴 모두 적용한다.
- 카페 브랜드의 정상·처리 필요 파일을 모두 확인하고, 카테고리 이름뿐 아니라 실제 메뉴 형태를 기준으로 판단한다. 차·에이드·주스·라떼·스무디·쉐이크·프라페·그라니따 등과 아이스크림 카테고리에 있는 마시는 라떼도 포함한다. 공식 중량 단위가 g여도 마시는 메뉴이면 `1잔`을 사용한다.
- 병·캔 포장 음료, 원액·원두 등 여러 잔으로 사용할 수 있는 상품, 여러 잔 세트는 `1잔`으로 일괄 변경하지 않는다. 확인된 `1병`, `1캔` 등 제품 형태에 맞는 단위를 유지한다.
- 빙수·아이스크림·아포가토·젤라또·케이크·푸드 등 먹는 메뉴는 컵에 담겼거나 커피·음료 카테고리에 있더라도 자동으로 `1잔`을 적용하지 않는다. 이런 메뉴의 원본 `1조각`, `2조각`, `1회분`, `1회 제공량`, `1개`, `1식` 등 표현은 유지한다.
- 위 `1잔` 적용 대상 외에 `150g`처럼 중량만 있고 개수·회분 표현이 없으면 중량에만 기록하고 단위량은 공란으로 둔다.
- 단위량 표기를 바꾸더라도 중량·영양성분의 공식 제공 기준과 수치는 그대로 유지하고 재계산하지 않는다.
- 조각 수·인분 수·한 판 중량·우유 선택별 영양값을 유추하지 않는다.

## 6. 정상·제외·처리 필요 분류

- 모든 표준 값이 같은 완전 중복은 한 행만 유지한다. 나머지는 삭제하고 처리 필요 파일이나 중복 횟수를 따로 만들지 않는다.
- 중량·열량·영양성분이 모두 없는 메뉴는 두 파일에서 모두 제외한다. 중량만 공개되어 있으면 영양정보 확인 대상으로 남길 수 있다.
- 사이즈·온도·도우·엣지·옵션이 다르면 별도 메뉴다. 전체 메뉴명과 옵션이 실제로 동일한데 값이 다를 때만 값 충돌로 분류한다.
- 중량·열량 등의 범위·복합값, 실제 원본 표의 구조 오류, 필수 정보 누락은 처리 필요로 분리하고 사유를 구체적으로 쓴다. 아래에서 제외한 영양성분 간 수치 관계 검사를 검토 사유로 추가하지 않는다.
- 파싱 결과만 이상하면 실제 화면과 표 배치를 다시 확인한다. 화면이 정상인 행을 파싱 오류 때문에 비정상으로 분류하지 않는다.
- 미공개 일부 성분은 공란을 허용한다. 없는 값을 채우거나 미공개라는 이유만으로 모든 메뉴를 비정상으로 만들지 않는다.
- 한 행에 처리 필요 사유가 여러 개 있으면 해결된 사유만 제거하고 남은 사유를 구체적으로 유지한다. 모든 사유가 해결된 경우 정상으로 이동하고 처리 필요 파일에서 제거한다.
- **열량 대비 영양성분 환산 열량은 계산하거나 비교하지 않는다.** 탄수화물·당류·단백질·지방·포화지방 등에 열량 계수를 곱해 공시 열량과 대조하는 검사를 하지 않으며, 불일치만으로 처리 필요로 분류하지 않는다.
- **지방·포화지방 등 영양성분 사이의 대소·합계·포함 관계도 검사하지 않는다.** 지방보다 포화지방이 높거나 낮은지 등을 검토 사유로 만들지 않고 공식값을 유지한다.
- 기존 처리 사유가 위 열량 환산 비교 또는 영양성분 간 수치 관계 검사뿐인 경우 정상으로 옮긴다. 실제 원본 구조 오류·범위값·단위 미확정 등 독립적인 다른 사유는 유지한다. 공식 영양값을 계산으로 보정하지 않는다.

## 7. Notion 저장과 기존 데이터

- 기존 `브랜드 영양성분`의 해당 카테고리에 브랜드 페이지를 두고 Excel 두 개를 첨부한다.
- 날짜·출처·정상/처리 필요 행 수·유형별 수·중량 기준·부호/단위 코드 규칙을 함께 기록한다.
- 기존 파일을 수정할 때는 현재 첨부 파일을 확인하고 최신 두 파일로 교체한다. 행 수나 분류가 바뀌면 페이지 설명도 맞춘다. 관련 없는 내용과 다른 브랜드는 보존한다.
- 결과 Excel·CSV·수집 캐시 등은 프로젝트 디렉터리에 남기지 않는다. 임시 작업은 `/tmp`에서 하고 최종 결과는 Notion에 저장한다.
- DB 변경·대량 import·인덱싱·마이그레이션은 별도 명시적 요청 없이 실행하지 않는다.

## 8. 업로드 전후 검증

1. 파일을 다시 읽어 22/24열 이름·순서, 숫자 셀 유형, 단일 시트, 행 수, 중복 여부를 확인한다.
2. 중량 단위는 숫자 0·1 또는 사유 있는 공란만 허용한다. g/ml/oz 문자열이 남지 않았는지 확인한다.
3. ‘미만·이하’ 원문이 모두 해당 숫자의 음수 셀로 저장되었는지 확인하고, 0·공란이 바뀌지 않았는지 확인한다. ‘이상·초과’가 음수로 잘못 변환되지 않았는지 확인한다.
4. 정상/처리 필요 이동은 해결된 사유에만 적용하고, 두 파일 사이에서도 완전 중복과 행 누락을 확인한다.
5. Notion 파일 업로드 후 페이지를 다시 읽어 두 첨부 파일과 행 수·분류·규칙 설명이 일치하는지 확인한다.
6. 실행한 검증과 남은 검토 항목을 보고한다.
7. 카페 브랜드의 정상·처리 필요 파일에서 잔 단위로 마시는 메뉴의 단위량이 모두 `1잔`인지 확인한다. 카테고리에 섞인 먹는 메뉴·병/캔 상품·원액·원두·세트는 별도로 구분한다.
