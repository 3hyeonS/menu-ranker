# 브랜드 메뉴·영양정보 수집 규칙

최종 갱신: 2026-10-26 (이슈 #3에서 처음부터 다시 수집하기로 하고 전면 개정, 59개 브랜드 병렬 수집 중 내린 결정, 고피자 재수집 결정, 단위량 개수 단위 통일, 메뉴 카테고리 대체 이름·기타 정리, 먹는 메뉴 단위량 `1개`·중량 기준과 정수 분할 개수 단위 반영)

브랜드 메뉴·영양정보를 수집·수정·재출력하는 모든 요청마다 **작업 시작 전에 이 문서 전체를 읽고** 따른다. 세션·터미널이 달라도 이 문서가 기준이다. 사용자의 새 지시가 이 문서보다 우선한다.

- 수집·수정 요청이 끝나면 이 문서에 추가할 만한 내용을 정리해 사용자에게 보여 주고, 허락을 받은 뒤 갱신한다.
- 이 문서의 기준에 해당하지 않는데 판단이 모호한 경우는 모두 처리 필요로 분리한다. 규칙으로 판별할 수 있는 것은 정상으로 처리하고, 판별할 수 없는 것은 사용자에게 묻는다.

## 1. 데이터 폴더

수집 결과는 **메인 체크아웃**(`/home/sehyeon/menu-ranker`)의 `brand-nutrition/`에 둔다. 이 폴더는 `.gitignore` 대상이며 커밋하지 않는다. 이슈별 worktree 안에 두면 머지 후 worktree를 정리할 때 함께 지워지므로, worktree 세션에서도 메인 체크아웃 경로에 쓴다.

```text
brand-nutrition/
  template.csv                  # 표준 23열 헤더만
  all-menus.csv                 # 전체 데이터: 모든 브랜드의 정상 행
  brand-info.csv                # 브랜드별 정보 (4절)
  legacy/                       # 2026-10-25 이전 데이터(참고용, 수정하지 않음)
  backup/<날짜>-<작업>/          # 일괄 수정 전 원본(사용자가 원본 유지를 요청한 경우, 수정하지 않음)
  tools/                        # 수집 공통 도구(nutri.py, crop.js), 브랜드 출처 목록(brand-sources.md), 예시 스크립트(examples/)
  brands/<공식 한글 브랜드명>/
    normal.csv                  # 정상 메뉴
    needs-review.csv            # 처리 필요 메뉴
```

- 모든 CSV는 Excel에서 바로 열리도록 **UTF-8(BOM) + CRLF**로 저장한다.
- 브랜드 폴더 이름은 공식 한글 브랜드명을 쓴다(예: `brands/파리바게뜨/`).
- 작업 순서: 브랜드를 수집해 정상·처리 필요로 분류 → `brands/<브랜드>/`에 두 파일 저장 → `all-menus.csv`에서 그 브랜드의 기존 행을 지우고 새 정상 행을 추가 → `brand-info.csv` 갱신.
- 처리 필요 행이 없어도 헤더만 있는 `needs-review.csv`를 만든다.
- `legacy/`의 이전 데이터는 시작점으로 쓰지 않는다. 빈 전체 데이터에서 다시 수집한다.
- 수집 중 내려받은 원본·캐시 같은 임시 파일은 세션 scratchpad나 `/tmp`에 두고 데이터 폴더에 남기지 않는다.
- 파일 저장은 `tools/nutri.py`의 `Collector`·`save()`로 한다. `save()`는 `brand-nutrition/.lock` 파일 잠금 안에서 브랜드 파일·`all-menus.csv`·`brand-info.csv`를 쓰고 11절 검증을 실행한다. 여러 세션이 동시에 수집하므로 `all-menus.csv`·`brand-info.csv`를 잠금 없이 직접 고치지 않는다.
- `nutri.norm()`은 6절의 값 정리(천 단위 쉼표, 단위 문자, `(12%)`·`775(38)` 같은 기준치 비율 괄호, 고카페인 표시 `*`, `불검출`, `미만·이하`, 범위값)를 처리한다. 이 밖의 표기는 호출하는 쪽에서 정리한다.
- 이미지로만 공시된 표는 `tools/crop.js`(sharp)로 잘라 확대해 판독하고, 숫자가 빽빽한 구간은 다시 확대해 대조한다. 1일 기준치 비율(%)이 함께 있으면 비율로 판독값을 교차 검사한다(7절).
- 사이트 보안(Wordfence 등)이 자동 접근을 막으면 헤더 위조 등으로 우회하지 않는다. 사용자에게 브라우저에서 목록을 받아 달라고 요청하고, 상세 페이지는 요청 간격을 2초 이상 두고 받는다. 이 경우 목록의 total과 받은 항목 수로 누락을 대조한다.

### 여러 세션으로 나눠 수집할 때

- 브랜드 목록은 사용자 제공 `식당_브랜드별_공식_메뉴_영양성분_출처_.pdf`의 카테고리(버거·베이커리·샌드위치·샐러드·치킨·카페·피자)별로 세션을 나눈다. 다른 세션 담당 브랜드는 건드리지 않는다.
- 각 세션은 브랜드 하나(또는 몇 개)를 마칠 때마다 사용자에게 결과와 판단 사항을 보고하고 확인을 받는다. 이슈 #3에 진행 댓글을 남긴다.
- 사용자가 새로 정한 규칙은 이슈 #3에 `## 결정` 댓글로 남긴다. 각 세션은 브랜드를 시작하기 전에 `gh issue view 3 --json comments --jq '.comments[].body'`로 다른 세션의 새 결정을 확인한다(`--comments` 옵션은 GitHub Projects(classic) 오류로 실패한다).
- 이 문서 수정은 조정 세션 한 곳에서만 PR로 한다. 다른 세션은 문서에 넣을 내용을 이슈 댓글로 제안한다.

## 2. 표준 열

정상 파일과 `all-menus.csv`, `template.csv`는 다음 23열의 이름과 순서를 그대로 쓴다.

```text
메뉴,브랜드,브랜드 카테고리,메뉴 카테고리,중량 단위,중량,총중량,단위량,칼로리,탄수화물,당류,당알코올,식이섬유,단백질,지방,포화지방,트랜스지방,불포화지방,나트륨,카페인,칼륨,콜레스테롤,알코올
```

- 처리 필요 파일은 23열 뒤에 `처리 유형`, `처리 사유` 두 열만 추가한다. 다른 보조 열은 만들지 않는다.
- `처리 유형`은 가능하면 다음 이름을 쓴다: `중량 누락`, `중량`(기준 중량·총중량 형식이나 크기 문제), `기준 중량 미상`, `범위값`, `값 형식`, `이상치`, `값 충돌`, `세트·콤보`, `구성품별 값`, `영양값 미공시`, `모든 값 0`, `메뉴명 판독`, `출처 확인`. 여럿이면 `, `로 잇는다.
- `처리 사유`는 무엇이 문제인지와 원문 값을 구체적으로 적는다. 사유가 여럿이면 모두 적고, 해결된 사유만 지운다. 모든 사유가 해결되면 정상으로 옮긴다.
- `scripts/import-restaurant-menus.ts`는 이 23열을 읽는다. `총중량`은 형식만 검증하고 DB에는 저장하지 않는다.

## 3. 수집 범위와 출처

- **공식 홈페이지에 게시된 정보만** 사용한다. 수집 요청과 함께 받은 링크·자료가 있으면 그것을 우선한다. 단, 받은 자료보다 공식 홈페이지에 새 버전이 있으면 홈페이지 최신본을 쓴다(예: KFC PDF `Ver. 20261013` 대신 홈페이지 `Ver. 20261020`).
- 메뉴 페이지의 영양성분표보다 최신인 영양성분표를 브랜드가 공지·소식 게시글로 따로 공시하면, 그 표로 브랜드 데이터를 전부 대체한다. 새 표에 없는 이전 메뉴는 남기지 않고, 메뉴 페이지가 이전 구성이면 메뉴 대조에 쓰지 않는다(예: 고피자 `promotion/detail/44`).
- 사용자는 브랜드마다 링크나 사진을 함께 준다.
  - 사진: 영양성분표 사진이다. 사진의 값을 그대로 옮기고, 읽을 수 없는 값은 추정하지 않고 처리 필요로 분리한다. 메뉴명 판독이 불확실해도 처리 필요(`메뉴명 판독`)로 분리한다.
  - 영양성분표 링크: 그 표를 기준으로 수집한다.
  - 메뉴 페이지 링크: 브랜드가 영양성분표를 따로 공시하지 않고 메뉴를 하나씩 눌러야 영양성분이 나오는 경우다. **모든 메뉴 카테고리와 하위 카테고리(탭·필터·더보기·페이지 넘김 포함)를 빠짐없이 확인**하고, 각 메뉴의 상세 페이지·팝업에서 영양성분을 모두 확인한다. 수집 후 카테고리별 메뉴 수를 홈페이지 목록과 대조해 누락이 없는지 확인한다.
  - 일부 브랜드는 메뉴 페이지의 `영양성분` 버튼·칸을 누르면 전체 영양성분표로 이어진다. 이런 표가 있으면 그 표를 영양성분표로 보고 아래 영양성분표 우선 규칙을 적용한다.
- 메뉴 페이지가 공식 API·내장 데이터로 표를 그리면 같은 응답을 수집해도 된다. 출처 URL에 페이지와 API 주소를 함께 적는다(예: 맥도날드 `/api/v1/kor/product/nutrition`, 버거킹 `BKR0347`). 그 응답에 화면 표보다 많은 성분(탄수화물·지방·콜레스테롤 등)이나 화면에 없는 기준(HTML 주석의 `영양성분은 100g 기준`)이 있으면 함께 쓴다. 화면에 같은 항목이 표시돼 있으면 화면 값을 쓴다.
- 요청 범위의 모든 하위 카테고리·개별 상세 페이지·공식 사이즈·온도·도우·옵션을 확인한다. 같은 제품이 여러 목록에 노출되면 한 번만 수집한다.
  - 베스트셀러·신메뉴·추천 같은 기획 목록과 기본 카테고리에 같은 값으로 함께 있으면 기본 카테고리 쪽을 남긴다. 기획 목록·NEW 영역에만 있으면 그 목록 이름(`NEW` 등 원문)을 카테고리로 쓴다. 기본 카테고리 여럿에 있으면 먼저 나온 카테고리를 쓴다.
  - 매장 형태별로 표가 나뉘면(예: 고피자 일반매장·2.0 매장) 모두 수집하고, 추가 표 행의 메뉴 카테고리 앞에 매장 구분을 붙인다(`2.0 매장 퍼스널 피자`). 기본 표와 이름·값이 같은 행은 중복으로 버린다.
- 공식 영양성분표에 현재 메뉴 목록에 없는 메뉴(단종 추정·토핑·소스)가 있어도 모두 수집한다. 메뉴 목록에는 있지만 영양성분표에 없는 메뉴는 제외하고 `brand-info.csv` 비고에 적는다.
- 메뉴 페이지형 사이트의 신제품 기획전 아카이브(과거 단종 제품)는 범위에서 빼고 현재 카테고리 목록을 기준으로 수집한다.
- 메뉴 카테고리는 공식 표·화면의 구분 이름을 그대로 쓴다. `영양성분표`처럼 출처를 나타내는 대체 이름은 카테고리로 쓰지 않는다. 영양성분표에서 카테고리를 찾을 수 없는 메뉴(표에 카테고리가 없거나, 표에 없어 메뉴 페이지 값으로 따로 수집한 메뉴)는 다음 순서로 정한다.
  1. 먼저 공식 홈페이지 메뉴 페이지에서 이름(공백 무시)이 같은 메뉴를 찾아 그 카테고리(탭·필터) 이름을 쓴다. 이름이 같은 메뉴가 없어도 세트 구성품(`menuComponents` 등)에 같은 이름이 있으면 그 세트의 카테고리를 쓴다(예: 메가커피 ARIH 7종 → 메뉴 페이지 필터 `음료`, 버거킹 `바삭킹8조각` → 사이드 세트 구성품이라 `사이드`).
  2. 메뉴 페이지에서도 찾을 수 없는 메뉴(단종 추정 메뉴·토핑·소스)는 메뉴 종류에 맞는 그 브랜드의 기존 카테고리에 넣고, 토핑은 `토핑`으로 쓴다. 판단 근거는 비고에 적는다(예: 버거킹 단종 와퍼 → `와퍼&주니어`, 패티·슬라이스치즈 → `토핑`).
  - 공식 표의 `기타`처럼 여러 종류가 섞인 카테고리는 사용자가 정한 브랜드만 나눈다. 같은 브랜드의 맞는 카테고리로 옮기고, 맞는 곳이 없으면 `음료`처럼 메뉴 종류를 나타내는 일반 이름을 쓴다(예: 피자헛 `기타` → 소스·피클 `사이드`, 음료 `음료`). 나누지 않은 공식 `기타`·`etc`는 원문 그대로 둔다.
- 사이즈·온도·도우·엣지·토핑·옵션이 다르면 별도 메뉴다. 이름 일부나 카테고리가 같다고 다른 제품을 합치지 않는다.
- 영양성분표와 각 메뉴 상세보기 정보가 다르면 **영양성분표 값**을 쓴다. 상세 값은 판독 교차 검사에만 쓴다.
- 상세 페이지에 자기 영양표 없이 다른 메뉴의 템플릿 블록·표만 남아 있으면 그 값을 쓰지 않는다. 같은 페이지의 PC·모바일 표 값이 다르면 차이가 작아도 값 충돌로 처리 필요에 둔다.
- 메뉴명은 원문 그대로 쓴다. `®`·`™`·띄어쓰기도 유지하고, 연속 공백만 하나로 줄인다. 원문에서 단어가 빠진 것처럼 보여도 오타로 보지 않는다.
  - 명백한 오타는 고친다(예: `말차라뗴` → `말차라떼`, `치즈스틱2개)`). 고친 내용은 `brand-info.csv` 비고에 원문과 함께 적는다.
  - 같은 말이 겹친 표기(`시그니처 스콘 (시그니처 스콘)`)는 하나로 정리한다.
  - 표 머리에 `품 명(선택)` 같은 범례가 있어 품명 뒤 괄호가 옵션 표시일 뿐이면(`젤라또와플(젤라또)`) 괄호를 뺀다.
  - 영양값의 오기로 보이는 값은 고치지 않고 7절대로 처리 필요로 분리한다(6절의 표기 보정은 예외).

## 4. 브랜드별 정보 (`brand-info.csv`)

브랜드 하나당 한 행. 열: `브랜드,브랜드 카테고리,공식 출처 URL,영양성분 공시일,수집일,뼈 포함 여부,정상 행 수,처리 필요 행 수,비고`

- 공식 출처 URL이 여럿이면 ` | `로 구분한다.
- 영양성분 공시일: 홈페이지·영양성분표에 적힌 공시일·게시일·개정일·기준일을 원문 그대로 적는다. 찾지 못하면 `공시일 확인 불가`로 적는다. 이미지 파일 경로의 날짜로 추정하지 않는다.
- 수집일: 실제 수집한 날짜(YYYY-MM-DD).
- 뼈 포함 여부: 치킨 등 뼈 있는 메뉴가 있는 브랜드만 `뼈 포함` / `뼈 제외` / `공시 없음` 중 하나를 적는다. 메뉴마다 다르면 `메뉴별 상이`로 적고 비고에 구분을 적는다. 해당 없는 브랜드는 공란.
- 비고: 영양 기준(예: 100g당, 1회 제공량 기준), 컵 용량 표, 브랜드가 공시한 주의 문구, 수집 시 내린 판단, 값에서 떼어 낸 주석(`*매장별 원재료 재고량에 따라 당 수치 상이`), 버린 보조 열·성분 등 참고할 만한 내용.
- 행 수는 해당 브랜드의 `normal.csv`, `needs-review.csv` 데이터 행 수와 일치해야 한다.

## 5. 중량·총중량·단위량

- **`중량`은 제품 총중량이 아니라 영양성분의 기준 중량**이다.
- `중량 단위`는 숫자로 저장한다: g=`0`, ml=`1`. 숫자 `0`은 유효한 g 코드다. g↔ml 변환은 하지 않는다. 먹는 메뉴라도 공시가 ml이면(`1회 제공량[ml]`, 컵용량 ml로 공시된 아이스크림·빙수) ml로 둔다. 단위 표기가 전혀 없으면 g로 본다.
- 총중량이 따로 있고 영양 기준 중량과 다르면, 총중량은 `총중량` 열에 숫자로, 기준 중량은 `중량` 열에 숫자로, `단위량` 열에는 기준 중량을 문자로 적는다(예: 중량 `100`, 총중량 `250`, 단위량 `100g`).
- 영양 기준 중량이 총중량보다 크면 처리 필요로 분리한다.
- 중량이 0이거나 없으면 처리 필요로 분리한다.
- 공시된 `기준 중량 × 총제공 횟수`가 총중량과 맞지 않으면 처리 필요로 분리한다. 단, 총제공 횟수가 기본값 1로 남은 경우는 제외한다.
- 치킨의 `조리 전 중량`·`원료육 기준 중량`·`OOg 이상`은 총중량에 쓰지 않고 비고에만 적는다.
- 중량 열 헤더가 `중량(g/ml)`처럼 단위를 함께 적었으면 음료는 ml(`1`), 먹는 메뉴는 g(`0`)로 해석한다.
- 음료인데 헤더가 `중량(g)`이어도 값이 음료 용량과 같으면(예: `PET 500ml` 제품 500, 컵 음료 380) ml(`1`)로 보정한다. 숫자는 그대로 두고 단위 코드만 바꾼다. 컵·병 용량 공시가 없어 같은지 확인할 수 없으면 g(`0`)로 둔다.
- 중량과 영양성분은 같은 기준을 써야 한다. 일부 성분만 기준이 다르면 처리 필요로 분리한다(예: 중량 50g, 탄수화물 10g, 단백질(100g당) 5g).

### 단위량

위 항목이 아래 항목보다 우선한다.

1. 단위량이 적혀 있거나 별도로 공시된 단위량이 있으면 그것을 쓴다. 상세 표의 `1회 제공량(개)`, 피자의 `2조각/150g`·`1회 단위(조각)`처럼 공시된 개수·조각 수도 여기에 해당한다.
2. 총중량이 기준 중량과 다르면 위 규칙대로 기준 중량을 문자로 적는다. 음료도 같다(예: 1.25L 병의 `200ml`, 콜드브루 원액 300g의 `40g`). 단, 피자·치킨에서 기준 중량이 총중량의 정확히 1/2이면 피자는 `반 판`, 한 마리 치킨은 `반 마리`로 쓴다. 통다리·윙처럼 부위 메뉴는 `반 마리`로 쓰지 않고 기준 중량을 쓴다.
   - 기준 중량이 총중량을 정수로 나눈 값(반올림 오차 1g 안팎)이고 메뉴 종류로 보아 한 조각·한 개가 분명하면 개수 단위로 쓴다(예: 고피자 레귤러 피자 1/5·라지 피자 1/8 → `1조각`, 도미노 `스와이시 치킨 윙(7조각)` 33g/231g·`더블 크런치 치킨텐더` → `1조각`, 뚜레쥬르 샌드위치 1/2 → `1/2개`, 뚜레쥬르 `겹겹이 치즈스틱(6개입)`·웨이퍼 샌드·`촉촉 반숙란` → `1개`).
   - 사이즈·도우와 상관없이 모든 메뉴에 같은 공시 기준(도미노 피자 150g, 100g·100ml당)은 조각이 아니므로 기준 중량을 쓴다. 비율이 1에 가까운 값(`한 입 햄치즈 패스트리(4개입)` 88g/89g)이나 병 음료(`200ml`), 순살치킨·콜드브루 원액처럼 정수로 나뉘지 않는 값도 기준 중량을 쓴다.
3. 음료는 단위량을 `1잔`으로 쓴다. 단, 병·페트 음료(500ml·1.25L, 메뉴명의 `(PET)` 등)는 `1병`, 캔(355·350ml 캔 음료)은 `1캔`으로 쓴다. 표에서 용기를 알 수 없으면 `1잔`으로 두고 사용자에게 캔·병 여부를 확인한다.
4. 위에 해당하지 않는 먹는 메뉴(중량이 총중량과 같거나 총중량이 없는 메뉴)는 브랜드·메뉴명·카테고리·중량을 모두 보고, `1개`로 표시해도 어색하지 않으면 `1개`, 어색하면 기준 중량을 문자로 쓴다(예: 중량 263g → `263g`).
   - `1개`: 버거·빵·샌드위치·랩·도넛·쿠키·케이크(조각·홀)·낱개 사이드·포장 소스·드레싱·피클, 컵 아이스크림·콘·빙수·아포가토·젤라또컵·컵과일(ml 공시도 `1개`), 샐러드·포케·볼·도시락·프로틴 박스, 감자튀김·웨지 포테이토·코울슬로·콘샐러드처럼 사이즈로 파는 사이드, 세트·콤보, 시즈닝·가루 소포장, 버거용 번·패티·필렛·슬라이스 치즈·에그, 스낵박스·치킨 박스 같은 박스 제품. `N개입` 상품도 기준 중량이 낱개 무게면 `1개`다.
   - 기준 중량: 파스타·밥·떡볶이·수프·스튜, 여러 조각이 든 사이드(어니언링·치즈볼·너겟·텐더·떡강정·윙), 피자 한 판, 더즌·하프팩·순살치킨처럼 여러 개가 든 팩, 봉지·상자 과자·캔디·젤리·차, 토핑·추가 재료·소스 양, 두 메뉴 묶음(`새우 + 치킨버거`), 기준 중량이 박스 전체로 보이는 `N개입` 상품, 100g당 공시 브랜드의 메뉴, 같은 표의 다른 메뉴와 비교해 기준 중량으로 보이는 값(예: 피자나라치킨공주 피자·치킨 150g).
   - 메뉴명에 개수·분할 표기가 있어도(`2P`·`(1/4개)`·`세 조각`·`(2+2)`·`X2`) `1개`가 아니면 기준 중량을 쓴다.
   - 낱개인지 여러 개인지, 단독 메뉴인지 옵션인지 판단하기 어려우면 사용자에게 확인한다.
- 개수 단위 `EA`·`ea`·`pc`·`pcs`는 `개`로 통일한다(예: `(1EA)` → `1개`, `5EA` → `5개`, `(2pcs)` → `2개`). 메뉴명은 원문 표기를 그대로 둔다.
- 빙수·아이스크림·케이크 등 먹는 메뉴는 컵에 담겼거나 음료 카테고리에 있어도 `1잔`으로 쓰지 않는다.
- 조각 수·인분 수·한 판 중량 같은 값을 유추하지 않는다. 단위량 2항의 정수 분할 예외만 기준 중량과 총중량의 비율로 개수 단위를 정한다.

## 6. 영양값 기록

- 공식 값만 기록한다. 미공개 값을 추정하거나 0으로 채우지 않는다. 공식 숫자 0은 그대로 둔다. 원문 `불검출`은 `0`으로 기록한다.
- `-`와 공란, 공식 설명상 '해당없음'인 표시는 빈 값으로 둔다. **일부 성분만 미공개인 메뉴는 정상**으로 처리한다.
- 값에서 단위·특수문자·기준치 비율 괄호를 없애고 숫자만 남긴다(`1,234mg` → `1234`, `775(38)` → `775`, 고카페인 표시 `156*` → `156`). 소수점은 유지한다. 값 뒤에 붙은 주석은 떼어 비고로 옮긴다.
- **`~g 미만`, `~ 이하`(`<`, `≤`, `<=` 포함)는 해당 숫자의 음수**로 기록한다(예: `1g 미만` → `-1`). 이것만 있는 행은 정상이다. `0 미만`·`0 이하`는 음수로 표현할 수 없으므로 처리 필요로 분리한다. `이상`·`초과`는 음수로 바꾸지 않고 처리 필요로 분리한다.
- 범위값은 `000~000` 원문 형태로 저장하고 **처리 필요**로 분리한다(예: `120~150`). 세트·콤보·팩처럼 구성에 따라 열량 범위만 공시된 메뉴도 수집해 처리 필요로 둔다. 단, 단일 공시값과 별도로 `총 열량 범위` 같은 보조 열이 있으면 보조 열은 저장하지 않고 비고에 적으며 행은 단일 값으로 정상 처리한다.
- 위 경우 외에 값이 단일 숫자가 아니면 처리 필요로 분리하고 원문을 해당 열에 남긴다(예: 카페인 `커피분말 5%`).
- 한 칸에 여러 값이 있으면:
  - 온도별 값 `a/b`(HOT/ICE): `<메뉴>(HOT)`·`<메뉴>(ICE)` 두 행으로 나눈다. 한쪽 값만 있는 칸은 두 행에 같은 값을 쓴다.
  - 매장 유형별 값 `a(휴게소 b)`: `<메뉴>`·`<메뉴>(휴게소)` 두 행으로 나눈다.
  - 두 용량·사이즈(`1.25L(500ml)`, `라지(점보)`): 용량·사이즈별 행으로 나눈다.
  - 단품·세트 값(`1개-약86, 세트-600`): 원문 그대로 두고 처리 필요로 보낸다.
  - 선물세트 구성품별 중량·값: 행으로 나누지 않고 처리 필요(`구성품별 값`)로 보낸다.
- 표기 보정(7절 "계산으로 보정하지 않는다"의 예외):
  - 공식 데이터에 값이 있는데 구분자 누락 등으로 화면에 `-`로 보이면 원본 데이터 값을 쓰고 정상으로 둔다(예: 맥도날드 `중량400ml` → 400ml).
  - 괄호가 깨진 값은 기준치 %로 확인되면 보정한다(예: 버거킹 포화지방 `28(185(` → 28, 15g의 185% ≈ 27.8g). 값과 %가 맞지 않으면(`130(28)`) 보정하지 않고 이상치로 둔다.
  - 단위 표기가 틀렸지만 기준치 %나 값 크기로 단위가 확실하면 그 단위로 기록한다(예: `콜레스테롤[g]`인데 값이 2~188 → mg, 나트륨 `g` 표기인데 %가 mg과 맞음 → mg). 확실하지 않으면 임의로 환산하지 않고 처리 필요로 분리한다.
- 표준 열이 없는 성분(타우린·비타민C·알룰로스 등)은 버리고 `brand-info.csv` 비고에 원문을 적는다. 에리스리톨은 `당알코올`, 조지방은 `지방` 열에 쓴다. 메뉴명 괄호에만 적힌 공식 영양값(예: `아메리카노(카페인 222mg)`)은 해당 열로 옮긴다.

## 7. 영양성분 이상치 검사

모든 행을 저장하기 전에 전체적으로 검사하고, 이상한 메뉴는 처리 필요로 분리해 사유를 구체적으로 적는다. 정해진 수치 기준은 두지 않고 수집하는 쪽에서 판단하되, 최소한 다음을 확인한다.

- 탄수화물·단백질·지방 등 성분 값이 기준 중량을 넘는 경우. `Ng당` 표기인데 값이 N g으로 불가능한 수준인 경우(100g당 2,065kcal)
- 당류가 탄수화물보다 크거나, 포화·트랜스지방이 지방보다 큰 경우처럼 포함 관계가 맞지 않는 경우
- 탄수화물·단백질·지방으로 계산한 열량이 공시 열량과 크게 다른 경우. 대체당이 공시됐거나 `제로슈가`·`저당` 이름에 당류가 거의 없는 음료가 탄수화물 대비 열량이 낮은 것은 이상치로 보지 않는다.
- 0kcal일 가능성이 낮은데 0kcal인 경우
- 같은 제품의 다른 사이즈·도우·옵션과 비교해 혼자 크게 튀는 값(예: 바질 마스카포네 L Thin/오리지널의 단백질 63g). 일반·디카페인처럼 같은 레시피 쌍에서 한 값만 다르면 양쪽 모두 이상치다.
- 같은 제품이 두 표에 다른 값으로 나오면 둘 다 이상치다.
- 같은 성분이 두 번 적힌 경우(예: `탄수화물 10g, 단백질 20g, 지방 5g, 단백질 12g`)
- 원본 표의 구조가 어긋난 경우. 파싱 결과만 이상하면 실제 화면과 표 배치를 다시 확인하고, 화면이 정상인 행을 파싱 오류 때문에 처리 필요로 보내지 않는다. 표 caption과 실제 머리글의 열 순서가 다르면 머리글을 따르고 값의 개연성으로 확인한다.

1일 기준치 비율(%)이 공시되면(이미지·HTML 표 모두) 값과 대조한다. 기준치는 나트륨 2,000mg, 당류 100g, 포화지방 15g, 단백질 55g 등 식약처 기준을 쓴다.

- 반올림 차이(±1%p), 정수 표기 값의 버림(22.9 → 22), 1~2g처럼 작은 정수 값의 % 차이는 정상이다.
- 둘 이상 성분이 함께 어긋나거나 반올림·버림으로 설명되지 않으면 이상치다.
- 표 전체에서 % 열 자체가 틀렸으면(예: %가 mg 값과 같게 적힘) 값은 그대로 쓰고 그 % 열만 검사에서 빼며 비고에 적는다.

양념 차이, 같은 제품의 부위(한마리·다리·윙봉 등)별 100g당 값 차이, 사이즈 간 10% 안팎의 차이처럼 설명할 수 있는 값은 정상으로 둔다. 이상치로 분류해도 공식 값을 계산으로 보정하지 않는다.

## 8. 중복 메뉴

- 메뉴명·카테고리·사이즈·토핑·옵션 등 하나의 메뉴로 특정할 수 있는 특성이 모두 같아야 중복이다.
- 같은 메뉴명에 영양값도 같으면 **하나만 정상에 남기고 나머지는 버린다**(처리 필요에 넣지 않는다). 값이 `-`와 `0`만 다르면 `-`를 0으로 보고 같은 값으로 처리한다.
- 같은 이름에 정상값 행과 중량까지 모두 0인 행이 있으면 정상값 행만 남기고 0값 행은 버린다. 정상값 행이 없는 모든 값 0 행은 처리 필요(`모든 값 0`)로 둔다.
- 메뉴명에서 수량만 다르고 중량·영양값(100g당 값 포함)이 같으면 하나만 정상에 남기고 나머지는 버린다. `하프`도 수량 표기로 본다.
- 띄어쓰기만 다른 메뉴명은 같은 메뉴다. 값이 같으면 한 행만 남기고, 다르면 값 충돌로 처리 필요에 둔다.
- 보냉백·포장 등 음식이 아닌 옵션만 다르고 중량·영양값이 같으면 옵션을 메뉴명에서 빼고 한 행으로 합친다(예: `말차빙수(보냉백 포함)`·`말차빙수(보냉백 미포함)` → `말차빙수`).
- 판매 채널·매장·행사 표기((리뷰)·(○○점)·(야구장)·(정가)·[특가] 등)가 붙은 변형은 기본 메뉴와 값이 같으면 버리고, 기본 메뉴가 없거나 값이 다르면 원문 이름을 유지한다.
- 메뉴 카테고리와 메뉴명이 완전히 같은데 영양값이 다르면 해당 행을 모두 처리 필요로 분리한다(값 충돌). 단품 값은 같고 세트 열량만 다른 경우처럼 일부만 다르면, 같은 단품은 하나만 정상에 남기고 값이 다른 세트 행들을 값 충돌로 분리한다.
- 같은 이름이 겹치지 않게 구분 이름을 붙인다. 이름이 겹치지 않으면 붙이지 않는다.
  - 세트·콤보·팩: 표 제목의 구분을 붙인다(`<메뉴> 세트`, `<메뉴> 콤보`). 해피밀처럼 원문 표기 방식이 있으면 그것을 따른다(`해피밀 <메뉴>`).
  - 카테고리 표로만 구분되는 같은 이름: 카테고리 구분을 붙인다(`오븐 닭다리살 포케`, `피자마루업 콤비네이션 피자`).
  - 사이즈 표가 나뉘어 같은 품명이 반복되면 사이즈를 붙인다(`<메뉴> L`·`<메뉴> R`). 사이즈 표기 없이 용량만 다르면 용량을 붙인다(`I-딥라떼(414ml)`).
- 브랜드 파일 사이, `all-menus.csv` 안에서도 중복이 없는지 확인한다.

1. 파일을 다시 읽어 BOM, 헤더(23열/25열) 이름·순서, 행 수를 확인한다.
2. `중량 단위`는 `0`·`1`만 있는지 확인하고, 정상 파일의 `중량`이 0·공란이 아닌지 확인한다.
3. 정상 파일의 숫자 열에 숫자가 아닌 값(범위값·단위 문자열 등)이 없는지 확인한다.
4. ‘미만·이하’ 원문이 모두 음수로 저장됐는지, 원래 0·공란이 바뀌지 않았는지 확인한다.
5. 브랜드 파일 안, 정상·처리 필요 파일 사이, `all-menus.csv` 안에 중복·누락이 없는지 확인한다.
6. `all-menus.csv`의 해당 브랜드 행이 `normal.csv`와 일치하는지 확인한다.
7. `brand-info.csv`의 행 수가 실제 파일과 일치하는지 확인한다.
8. 음료의 단위량이 `1잔`·`1병`·`1캔`이거나, 총중량이 기준 중량과 달라 기준 중량 문자(`200ml`)인지 확인한다.
9. 실행한 검증과 남은 처리 필요 항목을 보고한다.

## 12. 하지 않는 것

- DB 변경·`restaurant:import`(restaurant 테이블 전체 삭제 후 재삽입)·벡터 인덱싱·마이그레이션은 사용자의 별도 명시적 요청 없이 실행하지 않는다.
- 현재 import 스크립트는 음수 값과 범위값을 거부한다. ‘미만’ 음수 값은 import 스크립트를 수정해 처리하기로 했다(2026-10-25 결정, 처리 방식은 별도 작업에서 정한다). 수집 파일에는 이 문서대로 음수를 기록한다.
